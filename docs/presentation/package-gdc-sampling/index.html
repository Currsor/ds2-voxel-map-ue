02 · REQUIREMENTS

四个要求共同限定技术路线

03 / 13

必须是全三维

玩家需要从地图直接判断陡坡、断崖、死胡同和建筑空间。

不能增加美术工作量

地图数据应从最终游戏世界自动获得，而不是再制作一套地图专用资产。

内存与加载必须轻量

地图叠加在现有世界资源之上，必须保持较小体积并支持快速加载。

符合帧时间预算

缩放与导航不能引发卡顿，渲染成本必须与游戏其余系统共存。

05 · ATTEMPT A

高度图重建：适合占位，不适合作为最终数据

06 / 13
Game View ↔ Height + Color Map
× REJECTED

单值高度无法表达多层空间

对普通地表，它简单、稳定、生成快速；但同一个平面位置只能保存一个高度。

因此会丢失：
桥下空间、洞穴、悬挑、建筑内部，以及上下重叠的复杂结构。

GDC 中仍将它保留为正式体素地图完成前的临时占位方案。

优点：便宜、快速 · 限制：2.5DGDC 07

资产本体不等于最终像素

导出 Mesh 可以得到非常精确的几何，但它绕过了游戏运行时的最终材质组合。

缺少的信息包括：

09 · HEMISPHERE PASS

第一阶段：像摄影一样覆盖外部表面

10 / 13
Uniform camera distributionOuter surface coverage
XYZ
GDC 原始描述多个摄像机均匀分布在世界区块上方的半球区域，渲染多张画面。
我们的 UE 对应实现BakeHemisphereCapture 使用 Fibonacci Hemisphere 生成稳定、均匀的视图方向。
每个视图采什么SceneDepth 用于重建空间位置，BaseColor 提供不带光照的表面颜色。
能力边界适合地形和建筑外表面；仍会漏掉被上层结构遮挡的空间，因此必须进入 Slice Pass。
公开资料确认“均匀半球”；具体视角数属于工程复原参数Pass 01

10 · XYZ SLICE PASS

第二阶段：让摄像机穿过区块内部

11 / 13
Axis-aligned sweepOccluded space recovery
XYZ
XSlice 01 → NORTHO
YSlice 02 → NORTHO
ZSlice 03 → NORTHO
Bridge / Canyon / Interior半球视图无法覆盖的数据
GDC 原始描述沿每个坐标轴移动摄像机并渲染切片，用于捕捉桥下、峡谷内部和建筑内部。
我们的 UE 对应实现BakeXYZSliceCapture 使用三轴正交相机，并只接受当前 Slab 范围内的重建点。
为何限定 Slab如果正交视图接受射线上的所有表面，同一视图仍会被最近遮挡面主导；薄层约束让采样空间逐层推进。
与半球互补Hemisphere 提供更自然的外表面结果；Slice 专门提高内部与遮挡区域覆盖。

12 · POINT GRID

第三阶段：把浮点点云压缩成 Point Grid

13 / 13

不再保存每个点的浮点世界坐标，而是记录它在区块 Bounding Box 内的整数索引。

GridIndex = floor((WorldPosition − Bounds.Min) / CellSize)
Color[index] = Average(All colors at index)
  • 多个观测落到同一整数位置时合并为一个格点。
  • 同一位置的颜色由全部颜色求平均。
  • GDC 明确提出：发生冲突时优先采用 Hemisphere Pass，而非 Slice Pass。
  • 精度有所下降，但数据尺寸显著降低，并足以满足地图表现。
